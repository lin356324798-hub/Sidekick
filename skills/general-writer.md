# general-writer

> L1 通用写作兜底专家。覆盖公文、周报、方案、邮件、文案、散文、新媒体稿件等场景，采用 7 维质量评分框架（事实/逻辑/结构/语言/风格/受众/洞察）与 10 种文体适配矩阵。当 L0 路由未命中任何 L2 专家时作为兜底触发。适用于没有特定领域严格规范的通用写作任务。

## 使用说明（重要）

本技能从 WorkBuddy 导入。文中若提到 WorkBuddy 专有工具（如 `present_files`、`show_widget`、MCP 连接器、宿主图像/视频生成、腾讯文档授权、云端资料库等），这些在**本机（Sidekick / Termux）上并不存在**。遇到这类步骤，请改用本机已有能力实现，或直接跳过并说明原因。

**本文档的价值在于方法论与规范**（怎么写、怎么排版、怎么避坑）——照此执行即可，不必强行还原 WorkBuddy 的实现方式。

### Phase 1 — 主题理解
你需要详细思考如下要点：
1. 文体归类（正式公文？新媒体？内部周报？）→ 查询 `experts/general-writer/references/doc-type-matrix.md` 匹配字数与风格。
2. 目标读者画像（同事？客户？公众？）。
3. 核心信息点 3–5 条（用户已提供的 + 需要检索补全的）。
保存到 `output/params/topic.yaml`
   ```yaml
   detected_doc_type: "工作周报"
   target_length: 1000
   target_tone: "第一人称，正式度★★★☆☆"
   ```

### Phase 2 — Research（广度优先）
如果判断**完全不需要研究**时（纯格式化、纯模板填空），直接跳过，不需要传空参数；否则任何**先充分了解再动笔**"的阶段都不能跳过本阶段，典型场景包括：
- 写作前的素材准备
- 大纲生成前的行业背景摸底
- 针对某章节的信息缺口补充
你需要先参考**参数字典** `<plugin_root>/core/engines/deep-research/README.md` 生成驱动引擎的参数，保存到 `output/params/deep-research.yaml`。生成参数文件后，再读取 `<plugin_root>/core/engines/deep-research/engine.md` 执行 6 步状态机，产出信息库快照到 `snapshot_path`。

**默认deepredearch参数**如下仅供参考：

```yaml
# 必填参数（运行时由 Phase 1 结果填入）
topic: "<由 Phase 1 主题理解结果填入，一句话描述>"
tools: ["web_search"]          # L1 默认仅用网络检索

# 可选参数（已为 L1 通用写作配置默认值）
scope: "web"                   # 广度优先，可上网检索
max_loops: 2                   # 通用写作不需要过深研究
min_facts_required: 5          # 累计结构化事实数 ≥ 5
gap_check_strict: "relaxed"    # 宽松模式：Q1-Q4 必须通过，Q5-Q6 可容忍
search_dimensions:             # 必搜维度，默认通用两维
  - "数据"
  - "趋势"
tier_priority: []              # L1 不限定权威源优先级
snapshot_path: "output/research/{topic}_research.md"
```


### Phase 3 — Writing（纯写作 + 输出 critic_config）



---

#### Step 3.0 — 生成 critic_config

根据 Phase 1 产出的 `output/params/topic.yaml`，生成 `critic_config` 声明（由 doc-writer 消费）：

```yaml
# ===== 模式提示 =====
critic_mode_hint: "once"        # L1 默认 once；target_length ≥ 3000 时建议 per-section
force_mode: null                # L1 不强制，允许 skip

# ===== 评分标准 =====
rubrics_files:
  - "experts/general-writer/references/quality-framework.md"
  - "experts/general-writer/references/doc-type-matrix.md"
pass_score: 75
max_loops: 2

# ===== per-section 模式参数 =====
section_params:
  scope: "section"
  min_issues: 1
  min_instructions: 2

# ===== full 模式参数 =====
full_params:
  scope: "full"
  min_issues: 2
  min_instructions: 3

# ===== revision 模式参数 =====
revision_params:
  scope: "revision"
  min_issues: 1
  min_instructions: 1
```

**模式决策参考**（doc-writer 根据此 hint + 文档特征最终决定）：
```
if 用户明确要求不审 → skip（L1 允许）
elif target_length ≤ 1500 → once
elif detected_doc_type ∈ {小说, 调研报告, 方案, 年度总结, 长篇专题} → per-section
else → once
```

---

#### Step 3.1 — 执行写作

根据 critic_mode_hint 的预期，选择写作策略：

##### 预期 once 模式（短文）
```
1. 生成全文 draft → 落盘 output/draft/{title}_v0.md
```

##### 预期 per-section 模式（长文）
```
1. 生成大纲（章节清单）→ 落盘 output/draft/{title}_outline.md
2. 对每个章节 i:
   a. 生成章节 i 的 draft → 落盘 output/draft/{title}_ch{i}_v0.md
3. 合并全文 → 落盘 output/draft/{title}_merged_v0.md
```

##### 预期 skip 模式
```
1. 直接生成全文 draft → 落盘 output/draft/{title}_v0.md
```

---

#### Step 3.2 — 返回产物

将 draft + critic_config 一起返回给 doc-writer：

**本阶段的完整产物清单**（落盘到 `output/`）：

```
output/
├── params/
│   ├── topic.yaml              # Phase 1 产出
│   ├── deep-research.yaml      # Phase 2 产出
│   └── critic_config.yaml      # 本阶段产出（critic 声明）
├── research/
│   └── {topic}_research.md     # Phase 2 产出
└── draft/
    ├── {title}_outline.md      # per-section 模式才有
    ├── {title}_ch{i}_v0.md     # per-section 模式的章节稿
    ├── {title}_v0.md           # once/skip 模式的全文稿
    └── {title}_merged_v0.md    # per-section 模式合并后的全文稿
```

### references/doc-type-matrix.md

# 文体字数与风格矩阵（Doc Type Matrix）

> 本矩阵是 L1 General Writer 在 Deep Research 阶段的**文体定位参考**。不同文体有不同的字数基准、风格特征、关注点，需按此矩阵匹配。

---

## 一、 文体分类矩阵

| 文体 | 字数区间 | 正式度 | 人称 | 核心关注点 |
| --- | --- | --- | --- | --- |
| **公文 / 通知** | 300-800 | ★★★★★ | 第三人称（本单位 / 贵单位） | 准确、简洁、权威 |
| **商业报告** | 2000-5000 | ★★★★☆ | 第三人称（报告机构视角） | 数据支撑、结构完整、结论明确 |
| **工作周报** | 500-1500 | ★★★☆☆ | 第一人称（我 / 我们） | 成果导向、问题透明、下周计划 |
| **项目方案** | 3000-8000 | ★★★★☆ | 第三人称为主 | 目标、路径、风险、资源需求 |
| **产品文案** | 50-500 | ★★★☆☆ | 第二人称（您 / 你） | 痛点共鸣、利益点清晰、行动引导 |
| **新媒体稿（公众号）** | 1500-3000 | ★★☆☆☆ | 第一人称 / 第二人称 | 钩子开头、情绪节奏、传播性 |
| **邮件（正式）** | 100-500 | ★★★★☆ | 第二人称 | 主题明确、结构清晰（背景-请求-行动） |
| **散文 / 随笔** | 800-2500 | ★☆☆☆☆ | 第一人称 | 真诚、细节、情感共振 |
| **技术博客** | 1500-5000 | ★★★☆☆ | 第一人称 | 问题→方案→代码→反思 |
| **PPT 演讲稿** | 按页×150字 | ★★★☆☆ | 第一人称 | 一页一核心、节奏感、金句 |

---

## 二、 各文体的风格要点

### 2.1 公文 / 通知
```
✅ 明确指令：应、应当、须
✅ 正式称谓：本单位、贵单位、各部门
✅ 层级清晰：一、二、三... （一）（二）（三）... 1. 2. 3.
❌ 禁用表情符号、网络用语、情绪化表达
❌ 禁用口语化词（比如"咱们"、"挺好的"）
```

### 2.2 商业报告
```
✅ 先结论后论证（金字塔原理）
✅ 数据可视化描述（"同比增长 X%"、"环比下降 Y%"）
✅ 风险与机会并列
❌ 避免情感色彩（"惊喜"、"失望"等）
❌ 避免未经支撑的主观判断
```

### 2.3 工作周报
```
✅ 结构：本周成果 → 关键问题 → 下周计划 → 需要支持
✅ 成果量化：完成率 X%、上线功能 Y 个
✅ 问题透明：卡点、依赖、风险
❌ 避免"看起来很努力但没说做成什么"的水报告
❌ 避免所有细节堆砌，抓住重点
```

### 2.4 项目方案
```
✅ 标准结构：
   1. 背景与目标
   2. 需求分析
   3. 实施路径（里程碑）
   4. 资源需求（人、时、钱）
   5. 风险与应对
   6. 预期产出
✅ 图表化思考（虽然 Markdown 不一定能画，但要给出表格）
❌ 避免只给方案不给时间线
```

### 2.5 产品文案
```
✅ 结构：痛点共鸣 → 解决方案 → 独特优势 → 行动号召
✅ 短句、节奏感、押韵
✅ 使用第二人称拉近距离
❌ 避免自夸（让用户认可，而不是王婆卖瓜）
❌ 避免功能罗列而不提利益点
```

### 2.6 新媒体稿
```
✅ 开头三句话必须有钩子（数据冲击 / 反直觉观点 / 痛点共鸣）
✅ 段落短（不超过 4 行），插入小标题
✅ 情绪曲线：开头激发 → 中段铺垫 → 转折高潮 → 结尾金句
✅ 保留口语感，但不低俗
❌ 避免说教味太重
❌ 避免标题党骗流量却没有实料
```

### 2.7 邮件
```
正式邮件结构：
1. 问候语：您好 / Dear XX
2. 背景交代：一句话说清这封邮件来意
3. 核心请求：明确要求对方做什么
4. 时间节点：希望在 X 日前收到回复
5. 结尾致谢

避免事项：
❌ 没有主题行或主题过于模糊
❌ 一封邮件混多个请求（应拆分）
❌ 开头寒暄过长
```

### 2.8 技术博客
```
✅ 标准结构：
   - 问题场景（为什么要写这篇）
   - 技术方案（怎么解决）
   - 代码示例（可复现）
   - 踩坑记录（反思、替代方案）
✅ 代码块使用标准 markdown code fence
✅ 避免炫技，追求"读者能复现"
❌ 避免抄文档（应有自己的思考）
```

### references/quality-framework.md

# 通用写作质量评估框架（7 维打分）

> 本文件是 L1 General Writer 的**质量尺规**，由 Critic 引擎在 Adversarial Critic 阶段强制加载。
>
> 所有通用写作任务必须在**以下 7 个维度**独立打分（0-100），最终加权求总分。

---

## 一、 七维度定义

### D1：事实准确性（权重 20%）
- **定义**：文中提到的事实、数据、引用是否准确无误。
- **扣分项**：
  - 引用数据未标明来源：-10
  - 事实性错误（人名、时间、地点错误）：-30（严重）
  - 编造引用、虚构研究：-50（致命）
- **合格线**：≥ 70

### D2：逻辑严密性（权重 20%）
- **定义**：论点之间的因果、递进、对比关系是否自洽。
- **扣分项**：
  - 论点之间跳跃，缺少衔接：-10
  - 出现自相矛盾：-20
  - 结论与前文不匹配：-15
- **合格线**：≥ 70

### D3：结构清晰度（权重 15%）
- **定义**：整体结构是否有清晰的起承转合 / 总分总 / 分层论证。
- **扣分项**：
  - 没有明确段落划分：-10
  - 长段落不分层（超过 300 字的大段落）：-5/段
  - 无法概括段落核心（段落没有中心句）：-5/段
- **合格线**：≥ 70

### D4：语言精炼度（权重 15%）
- **定义**：是否存在冗余、啰嗦、车轱辘话。
- **扣分项**：
  - 重复表达同一观点：-5/处
  - 使用"总的来说"、"综上所述"等废话开头超过 2 次：-5
  - 单句超过 80 字未断：-3/处
- **合格线**：≥ 70

### D5：风格一致性（权重 10%）
- **定义**：全文语气、人称、风格是否前后统一。
- **扣分项**：
  - 第一/第三人称混用：-10
  - 正式/口语化风格混乱：-10
  - 中英混杂不规范（如无对应概念时的英文堆砌）：-5/处
- **合格线**：≥ 70

### D6：受众适配度（权重 10%）
- **定义**：表达是否符合目标读者的认知水平与关注点。
- **扣分项**：
  - 面向外行却使用大量专业术语不解释：-15
  - 面向专家却过度口语化：-10
  - 文中未体现对读者利益的关照：-10
- **合格线**：≥ 65（此维度较灵活）

### D7：创新与洞察（权重 10%）
- **定义**：是否有超越"罗列信息"的独特观点、类比、见解。
- **加分项**：
  - 提出新颖的类比或隐喻：+10
  - 给出反直觉但合理的结论：+10
  - 整合多源信息形成新洞察：+15
- **合格线**：≥ 60（此维度为鼓励性）

---

## 二、 加权总分计算

```
总分 = D1×0.20 + D2×0.20 + D3×0.15 + D4×0.15 + D5×0.10 + D6×0.10 + D7×0.10
```

**通过阈值**：总分 ≥ 75。

**单维度否决**：任一维度 < 60，即使总分达标，也必须重写该维度对应段落。

---

## 三、 Critic 输出格式要求

Critic 在审查时必须以以下结构化格式输出，便于 Harness 解析：

```markdown
## 七维评分报告

### D1 事实准确性：82/100
- 扣分：引用《XX报告》数据未标来源（-10）
- 修改建议：补充 "数据来源：XX研究院《2024 年度报告》"

### D2 逻辑严密性：75/100
- 扣分：第 3 段论点缺少过渡（-10）
- 修改建议：在第 3 段首句前增加承接句 "基于此..."

...（依此类推 D3-D7）

### 加权总分：78.5 / 100
### 是否通过：✅ 通过（总分 >= 75，且无维度 < 60）

### 需要重写的段落：
- 第 3 段（逻辑问题）
- 第 5 段（用词啰嗦）
```
